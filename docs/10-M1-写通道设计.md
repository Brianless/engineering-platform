# M1 写通道设计（第一刀：测设放点）

> 2026-11-22 23:25｜状态：**设计待确认，代码未动**
> 前置事实：M0 只读链路已闭环（D-01 / D-02 / D-03 均关闭），18 个工具全是 `sys_*` / `read_*` / `task_*`。

---

## 一、范围

### 做（第一刀）

只做**一个**写工具：按坐标表在图上放点/插桩号站标。

| 工具 | 作用 |
|---|---|
| `write_preview` | 无副作用。算 digest、算目标指纹、报告"将要新增 N 个对象到某图层" |
| `write_approve` | 由**人在 CAD 里点确认**后签发一次性 token |
| `write_insert_points` | 带 token 执行插入，返回句柄清单 |

### 不做（第一刀明确不碰）

- 删除 / 移动 / 修改已有图元（`erase`、`move`、`chprop`）—— 破坏性最大，留第二刀
- 保存、另存、打印、清理（`Save` / `QSAVE` / `PLOT` / `PURGE`）
- 图层/块定义的增删（`layer` / `block`）
- Civil 3D 原生对象写入（`Aecc*`）—— API 面太宽，且 2025 档不可用
- 多文档批量写

**为什么第一刀是放点**：测设的实际动作就是"把设计坐标落到图上"——插入是纯新增，不破坏既有图元，失败最容易回滚，是验证整条写链最安全的载体。

## 二、威胁模型（设计只对着这三条）

| # | 威胁 | 对策 |
|---|---|---|
| T1 | **模型自己批准自己**（幻觉/越权） | token 只能由 `write_approve` 签发，而它**在 CAD 里弹模态框要求人点"是"**。模型无法替人点 |
| T2 | **改错了还静默落盘** | 写工具**永不 Save**；不提交事务即整体回滚；返回前把新增句柄全部报回，可 `UNDO` 撤销 |
| T3 | **批准的与实际执行的不是一回事** | token 绑定 `paramsDigest + targetFingerprint + 文档身份 + 过期 + 单次`；任一不符即拒（E1002/E1006） |

不管的：多用户/权限分级、DWG 文件级加密、防本机恶意进程直连管道（由 `pipeguard.py` 与 Bearer 令牌覆盖）。

## 三、三层门禁

```
第 1 层  配置开关    config.write.enabled = false（默认）
                     false → 全部写工具恒 E2003，行为与 M0 完全一致
第 2 层  审批令牌    没有有效 token → E1006
                     有 token 但 digest/fingerprint 不符 → E1002
第 3 层  执行约束    只在主线程（MainThreadDispatcher）执行
                     单事务；不 Save；失败不提交
```

第 1 层是运维开关（改配置要重启 CAD），第 2 层是每次调用的硬门禁，第 3 层是代码纪律。

## 四、三步审批时序

```
我(模型)                宿主(MainThread)             人
   │                        │                        │
   ├─ write_preview ───────►│ 算 digest/fingerprint   │
   │◄── 摘要：新增 128 点 ───┤ 不写任何东西            │
   │                        │                        │
   ├─ (把摘要念给人听) ──────────────────────────────►│
   │                        │                        │
   ├─ write_approve ───────►│ 弹模态框："执行？"+摘要  │
   │                        ├───────────────────────►│ 点「是」
   │◄── approvalToken ──────┤ 校验点了「是」才签发    │
   │                        │                        │
   ├─ write_insert_points ─►│ 校验 token(签名/过期/单次/
   │   (带 token + digest)  │      digest/fingerprint)
   │                        ├─ 主线程事务内插入       │
   │◄── 句柄清单 + undo 提示─┤ 不提交前先记录数量      │
```

**关键点**：`write_approve` 是唯一能签发 token 的地方，而它必须**弹框并拿到人的点击**。模型可以调它，但没法替人点 —— 这就是 T1 的防线。

## 五、token 格式

```
token = base64url( payload ) + "." + base64url( HMACSHA256(secret, payload) )

payload = v1|<paramsDigest>|<targetFingerprint>|<docIdentity>|<expiryUnixMs>|<nonce>
```

| 项 | 说明 |
|---|---|
| `secret` | `%LOCALAPPDATA%\EngineeringPlatform\write-secret.bin`，32 字节随机，首次使用生成；ACL 仅当前用户 |
| `paramsDigest` | 参数规范化后的 SHA256（沿用既有 `ParamsDigest.Compute`，与 Python 侧同算法） |
| `targetFingerprint` | 执行时与当前文档指纹比对，防"批准 A 图、写进 B 图" |
| `docIdentity` | `doc.Name + db.Filename`，同上 |
| `expiryUnixMs` | 默认 **120 秒**。人点完就得用，过期重来 |
| `nonce` | 8 字节随机；内存表记录已用，**单次消费**。重启宿主即全部失效（这是有意的） |

校验顺序：签名 → 过期 → 未用过 → digest → fingerprint → docIdentity。任一失败即拒，且**不消耗 nonce**（避免误判把好 token 烧掉）。

## 六、工具契约

### `write_preview`

```json
// 入参
{ "kind": "insert_points",
  "points": [{"id":"K1+000","e":512345.678,"n":3210987.654,"z":412.5}],
  "layer": "EP-STAKEOUT", "block": null }
// 返回
{ "kind":"insert_points", "count":128, "layer":"EP-STAKEOUT",
  "paramsDigest":"sha256:…", "targetFingerprint":"fp1:…",
  "warnings":[], "willCreateLayer": true }
```

只算不写。`willCreateLayer=true` 表示图层不存在、执行时会新建 —— 这条必须让用户看到。

### `write_approve`

```json
// 入参
{ "kind":"insert_points", "paramsDigest":"sha256:…", "targetFingerprint":"fp1:…" }
// 返回
{ "approvalToken":"v1.…", "expiresInMs":120000, "confirmedBy":"modal_yes" }
```

宿主重算一次 params 的 digest？**不**——approve 只拿 preview 给的 digest，不重算（它没有 params）。
所以 digest 的可信来源是客户端的 `ParamsDigest.Compute(params)`；执行时宿主用**实际收到的 params 重算**并与 token 里的比 —— 这一步才是真正的"批准的和执行的是同一件事"。

### `write_insert_points`

```json
// 入参
{ "points":[…], "layer":"EP-STAKEOUT", "block":null,
  "paramsDigest":"sha256:…", "approvalToken":"v1.…" }
// 返回
{ "created":128, "layer":"EP-STAKEOUT", "handles":["2F1A","2F1B",…],
  "undoHint":"U 可撤销本次插入", "saved":false }
```

- 点对象类型：`block` 为空 → 插 `POINT`（`PDMODE` 用图面当前值）；给了块名 → 插块引用并用 `id` 填首个属性（属性 tag 由 `block` 同族的 map 决定，缺失则只用 POINT）
- 坐标按当前 `INSUNITS`/坐标系**不做任何换算**（显式声明：入参即图纸单位）
- 单次上限 5000 点（防一次塞爆），超限 → E1001

## 十、审批确认：**两个都要**（2026-11-22 23:30 决策）

用户选择「CAD 内弹框 + 聊天确认」双确认。实现上分两层，**性质不同，别混**：

| 层 | 在哪 | 谁证明 | 性质 |
|---|---|---|---|
| 流程确认 | 聊天里把摘要念给用户、用户回「执行」 | 模型带 `userConfirmation=true` | **流程纪律**：防模型自作主张跳过汇报。架构上不设防 |
| 硬确认 | CAD 里弹模态框、人点「是」 | 物理点击 | **硬防线**：模型没法替人点，这是唯一能把「模型幻觉」挡在外面的东西 |

`write_approve` 缺 `userConfirmation=true` → 直接 `E1001 chat_confirmation_required`（连弹框都不弹），
强制先走汇报；有了它才弹框，人点「否」→ `E1006 approval_denied_by_user`。

## 十二、双运行时（net48 + net8）—— 2026-11-23 00:10 落地

**问题**：AutoCAD 2024 跑 .NET Framework 4.8，AutoCAD 2025 起跑 .NET 8。同一个产品换了运行时，
net48 程序集装进 2025 会 `Method not found: NamedPipeServerStream..ctor(..., PipeSecurity)`（22:36 实测崩）。

**结论：能同时支持，不是"两个产品"，是"两个 TFM"。** 实测只有三处硬依赖：

| 坎 | 文件 | 改法 |
|---|---|---|
| 管道 ACL 8 参重载（Framework 专有） | `host/Pipe/PipeServer.cs` | `#if NET8_0_OR_GREATER` → `NamedPipeServerStreamAcl.Create(...)`；包 `System.IO.Pipes.AccessControl` |
| `JavaScriptSerializer`（System.Web.Extensions） | `host/Protocol/Json.cs` | 只换**解析**：`.NET 8` 用 `JsonDocument` 映射成同型 CLR 对象（整数→int/long、小数→double）；**序列化本来就是手写的，未动** |
| GAC 引用 / 单一 TFM | `host/EngineeringHost.csproj` | `TargetFrameworks=net48;net8.0-windows`；GAC 引用只给 net48；net8 用 `UseWindowsForms` |

**产物**（同一份源码）：
```
host/bin/Release/net48/EngineeringHost.dll           279,040 B
host/bin/Release/net8.0-windows/EngineeringHost.dll 280,576 B
```

**自动加载清单改成双组件**（`tools/bundle/.../PackageContents.xml`）：
包级 `SeriesMax=R25.9`，两个 `ComponentEntry` 各自带 `RuntimeRequirements`：
net48 → `R23.0~R24.3` 指向 `Contents/Windows/EngineeringHost.dll`；
net8 → `R25.0~R25.9` 指向 `Contents/Windows/net8/EngineeringHost.dll`。
`install_bundle.ps1` 同步部署两份。

**验收**：`tests/run_all.py` 1437/0、`tests/qa/qa_run_all.py` 742/0（改动后重跑，未退化）。

**未验证**：net8 档的**运行时**行为（管道 ACL、Idle 泵送、CAD 事件）—— 只验证了编译与打包。
需要在一台 AutoCAD 2025 上真机跑一遍；两档可以分别验证，互不影响。

**这为什么重要**：net8 档一通，2025 上就能"我们的网关/宿主 + 第三方基座（new-acad / civil3d-mcp）"并存 ——
基座提供覆盖面大的写方法（`addSurfaceBreakline`/`addLabel`/`addPipeToNetwork`…），我们提供审批、审计、
脱敏与读图语义。之前两者是互斥的（同一台机器只能选一档）。

**踩到的新坑（2025 特有）**：AutoCAD 2025 的命令行是 **WPF 控件且可被隐藏**（2024 是 Win32 停靠命令行）。
命令行隐藏时，向主窗口 SendInput 的按键会**静默落进绘图区被丢弃**，LISP 注入完全失效 ——
`Ctrl+9` 若把命令行为“切到隐藏”，此后所有自动化注入都无效，且没有任何报错。
以后在 2025 上做注入前，必须先确认命令行可见（枚举子窗口里存在命令行控件），再点击聚焦。

**未完成**：D-03 的系统变量订阅在 .NET 8 下的行为（需要改一次系统变量触发，注入通道受阻，待人工执行一条命令）。
间接证据：打开图纸过程中 `rev` 从 1 涨到 12385，说明 `Application.SystemVariableChanged` 在 .NET 8 下确实在回调
（2024 同场景只涨到 59，差异属事件频率不同，非缺陷）。

#### 2025 的命令行注入：四种方法全部失败（2026-11-23 00:15–00:30）

| 方法 | 结果 |
|---|---|
| SendInput `KEYEVENTF_UNICODE` + 主窗置前 | 按键被静默丢弃，命令行无回显 |
| 点击命令行控件（`337×93 @ (6,1257)`）再 SendInput | 同上 |
| `SendMessage(WM_CHAR)` 直接投给命令行句柄（父/子都试） | 同上 |
| `AttachThreadInput` + `SetFocus` 强夺焦点后再 SendInput | **焦点确实抢到了**（`GetFocus()` 返回命令行子控件），按键仍无回显 |
| 真实虚拟键码（VK_A/B/C + scan code） | 同上 |

**结论**：AutoCAD 2025 的命令行不接受合成输入（`SendInput` / `WM_CHAR` 皆无效），
而 2024 的 Win32 停靠命令行完全接受。**这只影响我们的自动化测试手段，不影响产品功能**
（读链路、写门禁、事件订阅都已在 2025 上通过管道验证）。

**补充（00:20 定位到根因）**：2025 的命令行其实是**独立的顶层 WPF 窗口**（`HwndWrapper[...]`，
1286×27 位于窗口底部），不在 MDI 框架的子窗口树里。`GetGUIThreadInfo` 显示焦点与光标（caret）都在它里面 ——
也就是说“焦点是对的”，但合成按键仍然不产生任何字符。结论不变：2025 命令行的输入栈不接收合成输入。
（顺带修正一个过程中的误判：我最初点的坐标是窗口左侧的另一个面板，命令行在 x≈803 起；
用 `PrintWindow` 抓这个 WPF 窗口只得到空白，因为它带透明层。）

要在 2025 上做自动化验证，只剩两条路：
1. 人工在命令行敲一次（一次性验证够用）；
2. 给宿主加一个**仅测试用**的 `ENG_EXEC` 命令（`SendStringToExecute`），但那是把任意 LISP 执行能力
   暴露到命令面 —— 除非限定为「只允许 exec 白名单文件」，否则不做。

| `write_preview`（kind=command，`(setvar "PDMODE" 36)`） | 回显命令 + 摘要 `sha256:9f173a0b…`，未执行 |
| `write_approve` | CAD 弹出「工程平台 · 写入确认」，框内显示**命令原文**；人点「是」后签发 376 字符令牌 |
| `write_command` | 令牌校验通过，命令排队执行，返回 `queued:true / saved:false` |

### D-03 的判决性证据（同一文档、指纹不变）

| 项 | 改前 | 改后 |
|---|---|---|
| `rev` | 18 | **19** |
| 指纹 | `fp1:3101f7e3c41c80a9626698ef68e3d5da` | **完全相同** |
| 该次读取 | — | `extract_breakdown`（重抽，非 cache_hit）|

终于拿到了不带混淆的证据：指纹未变 → 不是指纹变化导致的失效；rev +1 → **系统变量订阅在 .NET 8 下确实回调**。

### 本轮修掉的四个真 bug（都是"只在真机才暴露"的一类）

1. **写域门禁有两处**：`HostRuntime.ExecuteItem` 的前置闸 + `ToolRouter.Dispatch`。
   只改后者 → 永远 E2003。教训：改门禁必须 grep **所有**拒绝点（按错误码搜不够，要走同一 helper 的地方也算）。
2. **发现文件 `writeEnabled` 硬编码 false** → 改为 `HostCapabilities.WriteEnabled`。
3. **网关把写工具的结果压成「摘要 + resultRef」**，令牌被吞 → 三步审批在 MCP 侧不可用。
   修法：`write_*` 追加第三个 content 带完整载荷（写工具载荷 <2 KB）。
4. **`write_approve` 的摘要比较两边不对称**：`NormalizeDigest(入参)` 剥前缀，`recomputed` 带前缀 → 永远 E1002。
   修法：两侧都归一。

### 2025 自动化输入：定论

命令行的合成输入在 2025 上不可用（SendInput / WM_CHAR / AttachThreadInput+SetFocus / 真实 VK 全部无效）。
**但产品不需要它**：`write_command` 走的是 `SendStringToExecute`（进程内队列），绕开了 UI 输入栈。
以后在 2025 上做任何"要在命令行做的事"，走 `write_command` + 审批即可，不再需要人工敲键。

|---|---|

### B 路线（基座只做内部后端）的实现骨架

```
模型 → 我们的 MCP 工具（少数、稳定、snake_case、写域带 write_）
         ↓ 网关内部调用，不经模型
       BaseBridge（新增，host 侧或 gateway 侧）
         ↓ TCP 127.0.0.1:8080，auth=EP_BRIDGE_TOKEN
       new-acad 插件（430 方法，原样执行）
```

关键约束（三条，缺一条就会退化成绕过审批）：

1. **基座方法永不进入 `tools/list`**。`test_parity` 的命名契约与「写域必须 write_ 前缀」两条红线都靠这个维持。
2. **写类调用必须先拿我们的令牌**：`write_*` 工具的 handler 内部再转调基座，令牌校验在转调**之前**。
3. **审计要记基座方法名与参数摘要**（不记图纸内容），否则出问题无法复现。

首批拟暴露的薄工具（按使用频率与风险排序）：

#### 桥接层踩到的死锁与最终落点（2026-11-23 01:07–01:25）

**首次实现放在宿主里，立刻死锁：**

```
我们的工具在 CAD 主线程执行 → BaseClient 同步等基座
基座把 listSurfaces 排进它自己的主线程队列 → 主线程正被我们占着
基座日志：listSurfaces [1] cancelled durationMs=15005
我们这侧：IOException 读超时 → E3002 base_unreachable
```

**结论：基座调用不能发生在 CAD 主线程上。** 实现搬到网关：

| 文件 | 内容 |
|---|---|
| `mcp/base_bridge.py`（新） | Python TCP 客户端：单帧 JSON、令牌（env → `%LOCALAPPDATA%\EngineeringPlatform\base-token.txt` 兜底）、20s 超时、`BaseUnavailable` / `BaseCallFailed` 两类异常 |
| `mcp/engineering_mcp.py` | `GATEWAY_BASE_TOOLS` 分支：模型调用进来后**不转发宿主**，网关直接调基座并包成同形信封（预算/落库/审计复用既有路径） |
| `host/Tools/ReadToolHandlers.cs` | 原宿主实现改为**显式拒绝** `E2001 gateway_implemented:read_civil_surfaces` —— 入口保留但绝不执行，避免有人绕过网关再踩一次 15 秒死锁 |

**令牌为什么要文件兜底**：CAD 进程的环境变量是用户级设置（启动时继承），而网关由 MCP 客户端拉起，两者环境不一定同源。
CAD 侧仍只认 `EP_BRIDGE_TOKEN`（基座源码如此），文件是**给网关读的副本**，ACL 收紧到仅当前用户。

**真机结果**：`read_civil_surfaces` → `【Civil 曲面】共 0 个｜来源 基座 listSurfaces`（空白图，0 正确）。
测试：`tests/run_all.py` **1462/0**、`tests/qa/qa_run_all.py` **742/0**（含新增 `base_bridge` 到依赖白名单）。

**这条经验的普适形式**：任何"在我们的主线程回调里等另一个 CAD 内组件"的写法都会死锁；
跨组件调用只能放在**主线程之外**（网关、或宿主的后台线程 + 结果回传）。

3. 响应先回 `queued: true`，效果用 `read_civil_surfaces` 复核

## 十六、2025 崩溃事故：空曲面的三角形枚举（2026-11-24 13:26）

### 现象

`write_preview(kind=surface_breakline)` 刚执行，宿主连接断开，**AutoCAD 进程直接消失**（无弹窗、无日志收尾）。

### 定位（dotnet-dump 读转储，不是猜）

```
Exception type: System.ExecutionEngineException  HResult: 80131506
Thread 0 (main) stack:
  TinSurfaceTriangleEnumerator.MoveNext()
  Civil3dReader.CountOf(System.Object)
  Civil3dReader.CountOfMember(...)
  Civil3dReader.CollectSurfaces(...)
  Civil3dReader.Read(Document)
  SemanticExtractor.Extract(...)
  HostRuntime.GetSemanticModel(...)
  WriteToolHandlers.CurrentFingerprint(...)   ← 触发点
  WriteToolHandlers.Preview(...)
```

**根因不在预览逻辑**：预览为了拿指纹会抽一次语义模型，而语义模型在收集曲面属性时
对 `Triangles` 做了 `foreach` 计数。空 TIN 曲面（0 顶点）的三角形枚举器在 Civil 原生层触发 AV，
**不是可 catch 的托管异常**，进程立即终止。

这个缺陷一直存在——只是以前测的图纸没有曲面，从未走到这条路径。

### 修法（两条同时做）

1. **空曲面短路**：先读 `GetGeneralProperties().NumberOfPoints`，为 0 时直接把 `triangleCount` 记 0，
   **不进入枚举**。
2. **原生集合一律不枚举**：新增 `CountOfPropertyOnly`，只取 `ICollection.Count` 或 `Count` 属性；
   取不到就记"未知"（null），绝不 `foreach`。理由：原生枚举器在边界状态下的不变量不可知，
   宁可少一个属性，也不能拿进程稳定性去赌。

### 回归防线

`test_static_audit` 新增检查「原生集合不枚举（曲面三角形）」：
源码里必须出现 `CountOfPropertyOnly` 与 `pointCount.Value == 0`，
且**不得再出现** `CountOfMember(obj, new[] { "Triangles"`。

### 顺带发现：加载机制已换

同一天把加载从 Autoloader 换成**注册表 demand load**（`tools/register_plugin.ps1` /
`unregister_plugin.ps1`）：Autoloader 在 2025 上时灵时不灵且无提示，而手动 NETLOAD 又要靠人在命令行敲字。
换完之后宿主与基座都能随启动自动加载，零弹窗、零命令行。

## 十七、启动慢的真正原因：未签名弹框（2026-11-24 13:43–13:55）

### 量化结论

用「每 250ms 采样进程模块列表」得到时间线（`%TEMP%\ep\startup-modules.csv`，826 个模块）：

| 时刻 | 事件 |
|---|---|
| t=0 | acad.exe 进程启动 |
| t≈13.9 | `atrc250_arx.dll`（Vehicle Tracking，4.6 MB）|
| **t≈21.0** | `atrc250_crx.dll` —— **单次跳跃 +5.4 s，全场最大** |
| t≈26.0 | 模块列表停止增长（AutoCAD 卡住）|
| t=67.4 / 84.6 | 我们的宿主 / 基座才 initialize |

**结论：67–85 秒里，模块加载只占 ~26 秒，其余全卡在「安全性 - 未签名的可执行文件」模态框上等人点。**
Vehicle Tracking 的 5.4 秒是真实的第二大开销，但主因是弹框。

### 为什么 `TRUSTEDPATHS` 不够

我先写了 `TRUSTEDPATHS`（含插件目录），但重启后仍然弹框 —— 该变量值在注册表里确实还在，
说明它对**未签名的 .NET 程序集**不生效：AutoCAD 2025 按**文件哈希**记录「始终加载」，
每次重编译都是新哈希 → 重新弹框。TRUSTEDPATHS 只管本机路径的可执行文件信任，不等于发布者信任。

### 正解：代码签名 + 受信任发布者

1. 自签名代码签名证书 `CN=EngineeringPlatform Dev`（SHA256，10 年，EKU=代码签名）
2. 证书装入 `LocalMachine\Root` 与 `LocalMachine\TrustedPublisher`
3. `install_bundle.ps1` 每次安装**自动签名**（`Set-AuthenticodeSignature`），证书缺失时降级为警告不阻断
4. 证书备份：`tools/codesign/EngineeringPlatformDev.cer`

这样重编译也无需人工点确认——因为信任的是**发布者**，不是某个哈希。

### 顺带：已关闭的启动项（可回滚）

`tools/startup_profile.ps1`（-Action list / disable-cloud / disable-heavy / restore）：
本次关闭了 `App Manager`、`FeaturedApps`、`CloudAccess` 三个联网组件（LOADCTRLS=0），
备份在 `tools/backup/applications-*.json`。修好弹框后如仍慢，下一批可关 `PROJECT_EXPLORER` / `ATRA_AutoTrack*`。
